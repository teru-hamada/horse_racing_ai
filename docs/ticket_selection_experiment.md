# 推定回収率の上限を設けた買い目の並行検証

現行のおすすめ買い目と、確率補正の比較は維持する。別枠の `ev_cap2` で、補正なしの予測確率・同じ取得時オッズを使って買い目選定だけを比較する。

- 現行の候補条件を通った買い目に、推定回収率110〜200%（両端を含む）の条件を適用する。
- 条件適用後に現行スコア・推定回収率の順で並べ、各レース最大3点・各100円を確定する。
- 候補不足は点数を減らし、候補ゼロは見送り。取得オッズや予想自体が不足した場合とは区別する。
- 予想時に補正なし予想・候補・購入計画・固定条件・条件識別子を保存する。結果を見てから買い目を作り直さない。
- JRA公式払戻・返還で精算する。返還は的中に数えない。未確認の払戻を損失や回収率0%として扱わない。

保存先は `predictions/ticket_selection/<開催日>/`。`status.json` に予想の揃い具合、`ev_cap2/recommended_bets.csv` に固定した購入対象、`returns.json` と `ev_cap2/bets_results.csv` に公式精算を記録する。確率補正の `calibration/` とは独立する。

照合開始時に入力ファイルのハッシュを固定し、公開直前にも再確認する。条件定義・補正方式・金額・推定回収率の整合性も検査する。

結果HTMLには当日の精算状態と回収率・損益、同じ日付で両案の精算が完了した累計の購入額・払戻・損益・回収率を表示する。精算待ち・見送り・検証データ不足・検証開始前を区別する。新しい精算を公開する際、既存ページの比較欄も累計に合わせて更新する。

実装後に新規生成する予想から開始する。過去の予想に検証買い目を後付けせず、調査時のバックテストを将来検証の累計へ混ぜない。まず20開催日程度を再評価の目安とし、途中で条件を変えない。これは利益や統計的な十分性を保証する基準ではない。

今回の調査専用に作った `review_recent_ticket_selection.py`、`review_ticket_roi.py` と専用テスト、一時取得・確認プログラムは削除した。調査レポート・集計CSVと、取得済み公式HTML・払戻は確認用の記録として保持している。本番機能の回帰テストは `tests/test_ticket_selection_experiment.py` にまとめた。
