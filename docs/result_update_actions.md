# 確定結果DBの更新Actions

非公開データリポジトリ側の［確定結果DBの更新］で、結果HTMLの取得、開催日単位の登録、分割保存を行う。公開側の予想用モデル・本番参照SHAは変更しない。

## 実行内容

1. 非公開mainの最新スナップショットを取得する。
2. 完了記録から未処理の期間を決める。自動実行は古い順に最大7暦日まで処理する。
3. 完全な月間カレンダーで開催・非開催を確認する。
4. 掲載一覧と全レースの結果HTMLを新規取得し、識別子、重複、着順・走破時間、欠損理由を検証する。
5. 全レースが揃った開催日だけ、コピーDBへトランザクションで登録する。
6. 結果DBを含むスナップショットを64 MiB以下のpartにして非公開mainへ保存する。
7. 次回は保存後のmainを復元し、完了した日を再登録しない。

モデル、確率補正、予測用バンドル、特徴量DBはバイト単位で維持する。再学習や特徴量再生成は含まない。予想用バンドル内の履歴もこの処理では再生成しないため、今回のDB更新だけでは公開予想へ新しい履歴は反映されない。

## 手動実行と定期実行

手動実行では開始日・終了日を両方 `YYYY-MM-DD` で指定する。最大7暦日で、当日以降の結果は対象にできない。両方空欄なら、連続して確認済みの最終日の翌日から、昨日までの範囲で最大7日を処理する。

定期実行は日本時間02:25。`RESULT_UPDATE_ENABLED=true` の場合だけ実行する。初回の手動検証が終わるまではfalseで停止させる。GitHubのスケジュール起動には遅延があり得る。

過去の未取得期間が長い場合、1回で全期間の最新化を終えるものではない。保存した完了記録を使い、後続の実行で順に追いつく。手動で8月8日だけを取り込んでも、8月3日〜7日を処理済みにはしない。

## 保存と失敗

- 完了記録は `result_update_state.json`。日別のレース・行数と、連続して確認済みの最終日を保存する。
- 更新結果は非公開側の `result_update_report.json` とActionsのSummaryに記録する。
- 失敗した開催日はDBへ登録せず、次回の対象に残す。他の開催日が成功していれば、その分は保存できる。
- 取得失敗を「非開催」に置き換えない。新規HTTP取得には最大3回の再試行を設ける。
- 既に完了した日も掲載一覧・DBの件数を照合し、一致すれば結果の再取得・再登録を省く。
- DBの変更がなく完了記録だけが進む場合は、既存の分割ファイルを再利用する。
- 同じ指定で再実行し変更がなければ、再保存・コミットを行わない。
- workflowの同時実行制御と通常のGit pushで競合を検出し、強制pushはしない。
- HTMLは実行環境内に取得する。Gitには保存せず、再実行時に必要なら取り直す。

## 配置・権限

公開コード側の `.github/private-workflows/update-results.yml` を、非公開リポジトリの `.github/workflows/update-results.yml` に配置する。公開側のworkflowとしては実行しない。

非公開側は自身の `GITHUB_TOKEN` に `contents: write` を与えて保存する。追加の有料ストレージ、支払い設定、新規の書き込み用秘密鍵は不要。

`RESULT_UPDATE_CODE_REF` は、公開側コードの検証済み40文字コミットSHAに固定する。取り込みに必要なライブラリだけを、既存の非公開requirementsから固定して導入する。PyTorchや学習処理は使わない。

公開側の `PRIVATE_DATA_REF` は従来の予想用データを指したまま維持する。GUIで最新DBを取得する場合は、非公開側の更新後コミットSHAを明示して復元する。モデル更新を行う運用は別途設計する。
