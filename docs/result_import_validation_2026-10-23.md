# 結果取り込みのコピーDB検証（2026-10-23）

## 対象と方法

8月3日以降の更新に向けた最初の動作確認として、保存HTMLのある2026-08-09と2026-08-30を選んだ。全期間の一括更新ではない。

`scripts/validate_historical_import.py` で本番 `data/racing.duckdb` のコピーを作り、既存パーサー・登録関数を使ってhistoricalへ追加した。各日のnetkeiba掲載一覧は新たに取得し、中央競馬のレースIDを抽出して保存HTMLと照合した。地方競馬は対象外。

検証成果物はGit管理対象外の `data/analysis/result_import_validation_20261023_pass3/` に保存する。コピーDBは `racing_validation.duckdb`、機械可読の検査結果は `report.json`、解析した結果は `parsed_results.parquet`。

## 登録結果

- 8月9日：掲載一覧の36レースすべて解析。
- 8月30日：掲載一覧の36レースすべて解析。
- 合計72レース・974頭。既存historicalとキーの重複なし。
- historicalは266,720行から267,694行に増加。
- 同じ入力を2回登録し、件数・値が変わらず重複が増えないことを確認。
- 既存historicalの内容を保持することを確認。
- 着順・走破時間の欠損は6頭。元HTMLの行を確認したところ除外4頭、取消1頭、競走中止1頭。完走着順のある馬の走破時間欠損は0頭。

欠損6頭の原文と状態別件数は、検証成果物の `missing_finish_details.json` に保存した。

初回の検査は、既存登録関数がrace_oddsへ取得元管理用の4列を追加するため、厳密な列数比較で停止した。これは既存のスキーマ移行であり結果データの破損ではない。検証スクリプトを修正し、元から存在する列の全値が不変であること、新規4列がNULLであることを別々に確認するようにした。

関連する既存のDB登録検証テストは17件成功した（`python -m pytest tests/test_database_validation.py -q`）。

## 最終検証結果

修正版の実行は `status: ok` で終了し、13項目の検査がすべて成功した。処理時間は272.81秒（約4分33秒、掲載一覧のダウンロード時間は含まない）。

- baseline、race_entry、recent_speedは各974行を生成し、対象キーの不足・重複なし。
- 有効な着順がある968行に正解ラベルを付与し、保存済み前処理器で84列の入力に変換できた。非有限値なし、3着以内の正解は216行。
- 実行前後のSHA-256が一致し、本番の結果DB・特徴量DBは変更されていない。
- モデルの重み更新や精度・回収率の検証は行っていない。

再実行には新しい出力先が必要。取得済みの2つの `list_YYYYMMDD.html` をその出力先へコピーしてから、次を実行する。

```powershell
.venv/Scripts/python.exe scripts/validate_historical_import.py --output data/analysis/result_import_validation_next --dates 2026-08-09 2026-08-30
```

既存の検証DBへの上書きは拒否する。対象の結果HTMLも保存済みであることが必要で、不足する開催日は部分登録せず停止する。

## 利用上の範囲

このコピーは2開催日を追加した検証用であり、8月3日以降の全開催を収録していない。途中の履歴が不足するため、そのまま本番学習には使わない。特徴量生成の検査も動作確認として扱い、予測精度の評価とは区別する。

本番DB・本番特徴量DBの変更有無は、スクリプトの実行前後のSHA-256で確認する。最終合否・処理時間・特徴量生成結果は上記 `report.json` に記録する。モデルの再学習・切り替えやGitHub側への反映は実施しない。
